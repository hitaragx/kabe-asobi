# 要件定義：kabe-asobi（仮）

最終更新：2026-11-03

> 凡例：**【決定】** 合意済み／**【仮】** 提案段階で、作りながら見直す／**【未決】** これから決める

---

## 1. 概要

児童館の職員がスマホでClaudeに話しかけるだけで、その場にいる子どもに合った遊びが壁に立ち上がる。

- 【決定】ハッカソンのテーマ2「本来、誰にでも届くべきものを。」を主軸にする
- 【決定】動機（テーマ1の深さ）：インタラクティブ展示を作る側として現場に関わる中で、体験型の展示は専門の調整が要るため、予算や人手の限られた施設には届きにくいと感じてきた
- 目指す姿：インタラクティブコンテンツの民主化。専門のエンジニアがいなくても、施設の職員が自分たちの子どもに合わせた遊びを作れるようにする

## 2. 使い手と場面【決定】

| 項目 | 内容 |
|---|---|
| 使い手 | 児童館など子ども向け施設の職員。エンジニアはおらず、予算は小さい |
| 遊ぶ人 | 子ども（複数人が同時に遊ぶ） |
| ハッカソン後 | 職員自身がOSSとして使い続ける |

**遊びを作り替える理由**：季節にとらわれず、その日に遊ぶ人（年齢、人数、障がいの有無など）に合わせて、遊びの種類ごと変えたい。市販の製品は、用意されたカタログの範囲でしか替えられない。季節や地域の行事は、作り替える理由の一例として扱う。

**場面の例**
- 幼児と小学生が混ざる日：「小さい子の側は、的を大きく、ゆっくりにして」
- 車いすの子がいる日：「的を低い位置に出して」
- 小学生だけの日：「点数を競う対戦にして」

## 3. 体験の形【決定】

- 壁に短焦点プロジェクターで投影し、測域センサで壁に当たった位置を検出する
- ボール当て、手でのタッチなど、遊び方を選べる
- 測域センサを使う理由：大きな面を1台で覆える／手以外の物（ボール、お手玉）も検出できる／多人数が同時に遊べる。タッチパネルでは代わりにならない

## 4. デモで見せる場面【決定】

1. 話しかけるだけで、遊ぶ人に合った新しい遊びが壁に出る
2. 壁への合わせ込み（投影とセンサーの位置合わせ）を、Claudeが自分で終える
3. 遊んでいる最中に、その場で直せる

「遊びの記録をもとにClaudeが提案する」は今回の対象外。

## 5. 成功基準【決定】

| # | 基準 | 目標 |
|---|---|---|
| S1 | 話しかけてから新しい遊びが壁に出るまで | 5分以内 |
| S2 | 壁への合わせ込み | 職員の作業は印をタッチするだけ。5分以内、ずれ5cm以内 |
| S3 | 遊んでいる最中の修正 | 1分以内に反映 |
| S4 | 反応の遅れ（センサーが拾ってから画面が変わるまで） | 100ms以内（実測してから詰める） |
| S5 | 非エンジニアが使える | 説明なしで、話しかける→遊ぶ→直すの一連を最後までできる |

数字はデモ動画の中で実測して見せる。

## 6. 機能要件

### F1 入力【決定】
- 測域センサ1台（北陽電機 UST-20LX）。カメラは今回見送る
- 公開されている資料と公開ライブラリだけを使う
- センサーごとの違いは「入力アダプタ」に閉じ込め、出力を共通の形式（§8）にそろえる。安価な2D LiDARなど、別のセンサーにも差し替えられる作りにする

### F2 壁への合わせ込み【決定】
1. Claudeが壁に印を出し、「光った丸を順にタッチしてください」と職員に案内する
2. センサーの値から、センサーの座標と画面の座標の変換を計算する
3. 確認用の的を出してずれを測り、合格（5cm以内）するまでClaudeが自分で直す

検知する範囲、ノイズの閾値などは設定ファイルに持つ。

### F3 遊びの枠【決定】
- 「当たった位置を受け取り、絵を描き、音を鳴らす」ための枠と部品を用意する
- 遊びごとのコードは、Claudeがこの枠の中で書く。カタログにない遊びも作れ、壊れても影響の範囲が限られる
- 誰も遊んでいないときは待機のアニメーションを流し、一定時間操作がなければ最初に戻る

### F4 自動検証と戻し【決定】
- 新しい遊びや修正は、記録したボールの当たりを流して、動作・画面・フレームレートを確かめる。通ったものだけ壁に出す
- 「さっきのに戻して」で、一つ前の遊びにすぐ戻せる

### F5 記録・再生と模擬入力（最優先）
- センサーの入力を記録し、あとで再生できる
- センサーがなくても、合成したデータで遊びを動かせる
- 平日はセンサーに触れないため、開発の前提になる
- 実データの記録は11/6夜になるため、それまではセンサーの公開仕様（視野角、角度の細かさ、1回の走査にかかる時間、ノイズ）に合わせた模擬データで開発する。ボールが壁の面を一瞬だけ横切る様子、手が触れて離れる様子、複数人を再現する

### F6 障害時の振る舞い
- センサーが外れても画面が固まらず、待機状態に戻る
- 復帰したら自動で再接続する

### F7 イラストと効果音【決定】
- イラストはClaudeがSVGや図形で描き、効果音はブラウザの音声合成で作る。外部の素材を使わないので、権利の心配なくOSSに入れられる
- 絵柄のルール（フラット、太い輪郭、明るい色を数色、簡単な表情）をSkillに書き、遊びが変わっても雰囲気をそろえる
- 当たったときの演出（粒子、跳ね返り、効果音）は枠の部品として用意する
- 検証役のサブエージェントが、スクリーンショットで見た目（子どもに分かりやすいか）も確かめる
- 【仮】余裕があれば、職員が渡した画像（子どもの絵など）を的に使えるようにする。その画像はリポジトリに入れない
- 11/4に絵柄の試作を作り、11/5までに判断する。物足りなければ、職員の画像を使う案に切り替える

### F8 アニメーション【決定】：部品＋組み合わせ
- 枠の側に動きの部品を用意する
  - キャラクター：跳ねる、揺れる、まばたき、口パク、押しつぶれて戻る、歩く・飛ぶ
  - 移動：まっすぐ、ふわふわ漂う、決まった道筋をたどる、逃げる
  - 当たったとき：はじけて粒子が飛ぶ、回って消える、点数が飛び出す
  - 画面全体：場面の切り替え、紙吹雪、待機中のアニメーション
- キャラクターは体・目・口などのパーツに分けたSVGで描き、パーツごとに動かす
- Claudeは遊びごとに、部品の組み合わせ、速さ、当たったときの反応、点数を書く
- 部品にない動きは、Claudeが部品を追加して次の遊びから使い回す。追加した部品も自動検証の対象にする

### F9 ゲームのルール【決定】：型＋Claudeがアレンジ
- ルールの型：的当て／全部消す／みんなで協力／チーム対戦／色ぬり・陣取り／終わりのない遊び
- Claudeが遊びごとに決めるもの：終わり方、点数の有無、チーム分け、難しさ（的の大きさ・速さ・数）、場所ごとの設定（年齢別の区画、低い位置の的など）。型にないルールはClaudeが書く
- 作る前に職員に聞くのは、年齢と人数だけ（分からなければ1〜2問）。細かい点は壁に出してから直す
- 指定がなければ、出入り自由の遊び方にする。時間制は頼まれたときだけ
- 子ども向けの決まり（Skillに書いて必ず守らせる）
  - 年齢が低いときは、勝ち負けを出さない
  - 1回は1〜2分で終わるか、出入り自由にする
  - ボールの遊びでは、壁に近づかなくて済む配置にする。タッチとボールを同じ時間に混ぜない。柔らかいボールを前提にする

## 7. Claudeの機能の使い分け【決定】

| 機能 | 役割 |
|---|---|
| 職員の入口 | 専用のスマホ画面（Mac上のローカルWebサーバー、同じWi-Fiの中だけ・合言葉つきURL）→ Claude Agent SDK → PC上の Claude Code（11/4 に変更。下の「変更の記録」） |
| Skills | `new-game`（遊びを作る手順、絵柄のルール、子ども向けの決まり）／`calibrate`（壁への合わせ込み）／`tune`（遊んでいる最中の調整） |
| MCP | 自作の「壁サーバー」。センサーが今拾っている位置、投影中の画面、遊びの切り替えと戻しを、Claudeが道具として使える |
| サブエージェント | 検証役。記録した当たりを流し、動作・画面・フレームレート・見た目を確かめて合否を返す。軽量モデルで動かす |
| フック | 遊びのコードを編集したら自動で検証を走らせる／危ない操作を止める／コミット前に禁止語とAPIキーを検出する（禁止語リストはリポジトリに入れない） |
| モデル | 職員との会話と遊びの設計は上位モデル、検証は軽量モデル |
| CLAUDE.md | 構成、共通の形式、センサーの前提、職員向けの話し方（専門用語を使わない） |

見せたい新しさ：Claudeが画面の中で完結せず、センサーを読んで物理の空間に自分で合わせ込む。

## 8. システム構成

```
[測域センサ UST-20LX] ── LAN ── [Mac]
                                 ├─ 入力アダプタ（点群 → 当たり位置、共通の形式へ）
                                 ├─ 壁サーバー（MCP）
                                 ├─ 遊びの枠（ブラウザ、TypeScript＋PixiJS）── [短焦点プロジェクター] → 壁
                                 └─ Claude Code ←── Remote Control ── [職員のスマホ]
```

| 要素 | 内容 | 状態 |
|---|---|---|
| PC | Mac単体 | 【決定】 |
| 描画 | ブラウザ（TypeScript＋PixiJS） | 【決定】 |
| Raspberry Pi | 使わない前提で作り、余裕があれば土曜に判断 | 【決定】 |
| センサーの接続 | 11/3夜はルーターのLANポート経由（MacはWi-Fi）。土曜までにUSB-CのLANアダプタを買い、計測と撮影は有線で行う | 【決定】 |
| 入力→描画の通信 | WebSocket＋JSON | 【仮】 |

### 共通の形式（案）【仮】

```json
{
  "v": 1,
  "source": "lidar-1",
  "seq": 12345,
  "t_capture": 1762142400123,
  "points": [
    { "id": 3, "x": 0.42, "y": 0.77, "vx": 0.01, "vy": -0.02, "conf": 0.9 }
  ],
  "events": [
    { "type": "hit", "id": 3, "x": 0.42, "y": 0.77 }
  ]
}
```

座標は合わせ込み後の画面の正規化座標（0〜1）。【未決】合わせ込みを入力アダプタと描画のどちらで行うか。

## 9. 非機能要件【仮】

| 項目 | 目標 |
|---|---|
| 反応の遅れ | 100ms以内 |
| フレームレート | 60fps |
| 同時に遊べる人数 | 3人以上 |
| 連続稼働 | デモ中に止まらない（目安1時間） |
| 動作確認環境 | macOS |

## 10. 対象外

- カメラ入力
- 遊びの記録をもとにした提案
- 管理画面、遠隔監視
- 骨格推定などの重いAI処理
- 家庭用電源を扱うリレー制御

## 11. OSS公開と安全のルール

- 【決定】すべてハッカソン期間中に新しく作る。既存のコード・素材・名称は使わない
- 【決定】リポジトリは提出前に履歴全体を見直してから公開する
- 【仮】勤務先のコード、製品固有の処理、現場で調整したパラメータの値を持ち込まない
- 【仮】業務で入手したSDKや非公開の資料は使わない。公開資料と公開ライブラリだけを使う
- 【仮】README、コミットメッセージ、PROGRESS.md、TASKS.mdに、顧客名・施設名・製品名・案件の話を書かない
- 【仮】ログや記録データに、コンピュータ名・ユーザー名・絶対パス・ネットワーク情報を残さない
- 【仮】カメラの生映像、子どもが映った映像はリポジトリに入れない
- 【仮】コミット前に、禁止語とAPIキーを検出するフックを入れる
- 【仮】試用の撮影では、子どもの名前・学校名・家の外観が映らないようにする。顔を映すかは家族で決める

## 13. リスクと対策

| リスク | 対策 |
|---|---|
| 「AIでゲームを作った」作品に埋もれる | 動画の山場を「その場の子どもに合わせて直す」と「Claudeが自分で壁に合わせ込む」にする |
| 実機を触れるのが実質土日だけ | 平日は記録データと模擬入力で仕上げる（F5を最優先） |
| 見た目が素朴に見える | 絵柄のルールと当たったときの演出を作り込む。11/5に判断し、必要なら職員の画像を使う |
| 「既存ツールでできるのでは」と見られる | 専門家向けの高機能ツール（使いこなせる人が要る）、市販のテンプレート製品（カタログの範囲だけ）との違いを示す。Claudeが遊びのコードそのものを書き、壁に合わせ込む |
| 既存の展示の作り直しと見られる | 題材・道具・見た目を、既存の事例とはっきり区別する |
| ハードの不調で時間を失う | 早い段階でセンサー単体の動作を確かめる |
| 使用量の上限 | 重い作業は週末に寄せる |

## 14. 将来構想（今回は実装しない）【決定】

インタラクティブコンテンツの民主化。Kinectなどの深度カメラ、カメラ、安価なLiDAR、タッチパネルにも対応できるプラットフォームにする。

- 今回の設計で備えること：センサーの違いは入力アダプタに閉じ込め、遊びは共通の形式だけを受け取る。共通の形式とアダプタの追加手順を文書にする
- 【仮】将来：センサーの資料を渡すと、Claudeがアダプタを書いて合わせ込みまで済ませるSkill（`add-sensor`）

## 変更の記録

- 11/4【決定】職員の入口を「スマホのClaudeアプリ（Remote Control）」から「専用のスマホ画面」に変更
  - 理由：非エンジニアが安心してそのまま使える形にするため（審査基準「深さと実行力」「デモ」）。Claude アプリの画面には道具の記録やコードの変更が出て、職員には難しく見える
  - 画面：壁の今の画面（ライブ）、ボタン（さっきのに戻す・壁に合わせる・遊びをえらぶ）、話しかける欄（音声入力）、よく使う頼みごとのボタン。チャットだけの画面にはしない
  - 裏側：Claude Agent SDK で、プロジェクトの CLAUDE.md・Skills・サブエージェント・フック・壁サーバーをそのまま使う
  - 認証：APIキー（$500 のクレジット）。Agent SDK の利用規定で、職員など他の人が使う製品に claude.ai のログインは使えないため
  - 職員モードでは、使える道具を絞る（シェル・Webは使わない。許可の確認は出さず、許可されていない操作は断る）。1回の頼みごとの上限は $3
  - 開発中の Remote Control は、そのまま開発用に使う（APIキーはスマホ画面のサーバーだけに渡す）
