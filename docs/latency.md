# 反応の遅れの測り方

目標：ボールや手が当たってから、壁の絵が反応するまで **100ms 以内**。

遅れは次の5つに分かれます。

| # | 区間 | 測り方 | 目安 |
|---|---|---|---|
| 1 | センサーの中（光が当たってから、1回転分のデータが届くまで） | 仕様から見積もる（1回転 25ms） | 平均 約13ms、最大 約25ms |
| 2 | 当たり検出・座標変換（ハブ） | `npm run latency` | 模擬センサーで中央 0ms |
| 3 | ハブ → 壁の画面（WebSocket） | `npm run latency` | 模擬センサーで中央 9ms |
| 4 | 遊びに届く → 反応を描いた画面ができる | `npm run latency` | 模擬センサーで中央 0ms |
| 5 | 画面の書き換えと、プロジェクターが映すまで | スローモーション撮影 | 機種しだい（20〜50ms ほど） |

2〜4 は、壁の画面が当たりのたびに自分で記録しています（直近200件）。1 と 5 は、スローモーション撮影で全体を測って確かめます。

## A. ソフトウェアの部分（2〜4）

本番と同じ構成（センサー・ハブ・壁の画面）を動かしたまま、別のターミナルで：

```
npm run latency                 # 20秒、当たりを集めて内訳を出す
npm run latency -- --seconds 40 # 長めに集める
npm run latency -- --sim        # センサーなしの確認（模擬センサーと壁の画面を自分で起動する）
```

壁にボールを当てる・手でタッチすると、件数が増えていきます。最後に、区間ごとの中央の値と、遅い方（95%）の値が出ます。
壁の画面を `?debug=1` で開くと、左上にも中央の値（センサーを受け取ってから遊びに届くまで）が出ます。

**11/4 の結果（模擬センサー、画面なしのブラウザ）**：27件、合計の中央 10ms、遅い方 17ms。
1 と 5 を足した見込みは約 60ms（プロジェクターを 20ms と仮定）。

## B. 全体（センサーに当たってから、壁の絵が変わるまで）

iPhone のスローモーション（240fps＝1コマ約4.2ms）で、手と壁の絵を同じ画面に入れて撮ります。

1. 壁の画面を `http://127.0.0.1:5173/?debug=1` で開く（当たった所に、すぐ紫の輪が出る）
2. iPhone をカメラ → スロー（240fps）にし、壁の横から、手と投影がどちらも映る向きで構える
3. 手のひらを、壁に向かってすばやくまっすぐ当てる。10回ほど、場所を変えて
4. 写真アプリで1コマずつ送り、次の2つのコマ番号を数える
   - 手が壁に触れたコマ（センサーの光は壁から数cm手前を通るので、実際にはそれより少し前に検出が始まる。触れたコマを起点にすると、遅れは少し短めに出る）
   - 紫の輪が最初に見えたコマ
5. （輪のコマ − 触れたコマ）× 4.2ms を、10回の中央の値で記録する

ボールでも同じように測れます（壁に当たったコマを起点にする）。

### 記録の書き方（PROGRESS.md と動画の数字に使う）

```
反応の遅れ（全体、スローモーション 240fps、10回の中央）：〇〇ms
  ソフトウェアの部分（npm run latency、〇件）：中央 〇ms、遅い方 〇ms
  プロジェクター：（機種名は書かない）
```

## 100ms を超えたときに見るところ

| 大きい区間 | 見るところ |
|---|---|
| 3（WebSocket） | 壁の画面のブラウザが重い（FPS が 60 より低い）。遊びを軽くする、ほかのタブを閉じる |
| 4（画面ができるまで） | 遊びの処理が重い。`npm run verify` の FPS を確かめる |
| 5（プロジェクター） | プロジェクターの「ゲームモード」「低遅延モード」をオンにする。映像を補正する機能（台形補正、ノイズ除去）を切る |
| 全体だけ大きい | Mac が省電力になっていないか。電源につなぐ |
